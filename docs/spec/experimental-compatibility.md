# Experimental compatibility and diagnostics policy

Status: development activation of `0.2.0-alpha.1` / language `0.2`. The existing `0.1.0-m3.8b` release is unchanged. This policy does not announce a new release or promise compatibility across all 0.x versions.

## Identities and upgrade rules

| Identity | Current value | Compatibility meaning |
| --- | --- | --- |
| Compiler | `0.2.0-alpha.1` | Exact producer version required by the current artifact reader |
| Language | `0.2` | Implemented subset is listed in development status; the version is not a claim that every planned feature exists |
| ABI | `1` | Fixed/solution tree encoding, validation and currying convention |
| Target profile | `chia-clvm-0.19-strict-v1` | Pinned local VM dialect, flags and dependencies; not a universal network consensus profile |
| Manifest and CLI JSON envelope | `schema_version: 1` | Structural format version; distinct from compiler, language and ABI versions |
| Optimization | `none` | Required lowering still affects generated bytes; no optional optimizer modes |

`0xbasic --version` emits a JSON object with compiler, language, ABI and target-profile identifiers, followed by a newline. Invoke it without `--json`; the current standalone `--version` and `--help` forms do not accept additional flags. Normal commands accept `--json` and use the envelope specified in [CLI v1](cli-v1.md).

For experimental builds, changes to accepted syntax, semantics, generated bytes, observable CLI behavior or artifact interpretation require a distinct compiler version and a documented migration/compatibility decision. Documentation and test-only changes need no compiler version bump. An incompatible ABI, dialect/profile or JSON schema change also requires changing its own identifier; do not conceal it behind a compiler-only bump. Diagnostic prose may improve within an existing code's meaning, but a code must not silently acquire an unrelated meaning.

No blanket source or artifact compatibility is promised between experimental compiler versions. Preserve the original source, normalized fixed bindings, solution data, complete artifact directory and build provenance. On an upgrade, rebuild into a new directory, compare program bytes and both kinds of hash, and run relevant conformance and spend-validation tests before adopting the new artifact. Do not edit version fields to force an old artifact through a newer reader.

The current reader requires matching compiler, language, ABI, target profile, manifest schema and optimization identifiers. It rejects unsupported values with E0400/exit 2. A mismatched recorded Rust version is an artifact-provenance failure (E0600/exit 4). Source and Cargo.lock digests must be well-formed, but loading does not fetch those files or compare the recorded lock digest with the running CLI's lock. See [artifact reader guarantees](cli-v1.md#files-and-manifest); internal consistency is not proof of authorship or correspondence to advertised source.

Reproducible builds require the exact source bytes, bindings, compiler revision/version, Rust toolchain, Cargo.lock and target profile. Preserve all of them; the manifest records identities and hashes, not a source/dependency archive. Toolchain/dependency changes need explicit review even when generated bytes happen to match. CLI binary digests may differ by platform; artifact reproducibility is a separate assertion.

## Puzzle identity and execution scope

The [artifact workflow](artifact-workflow.md) provides a same-version rebuild exercise, comparison script and guidance for evaluating a future upgrade. It does not assume a newer compiler can read old manifests.

Serialized-byte SHA-256 and CLVM tree hash are different values. A changed bound puzzle hash identifies a different puzzle and cannot change the spending rules of an existing coin. Archive the matching reveal and supported tooling needed to exercise the original contract. Normalized equivalent fixed values may yield identical artifacts; source edits may change only provenance or may change puzzle bytes. Compare actual outputs rather than assuming either outcome.

Keep the ABI 1 binding wrapper, declaration-order schemas, canonical scalar encodings and eager raw-input guards unless an explicit compatibility change is approved and tested. AST/IR debug representations from `explain` are compiler-versioned inspection formats, not stable standalone interchange schemas.

`run` establishes local CLVM execution only. It does not validate a coin's existence, signatures, timelocks or block inclusion. SpendSim and isolated full-node tests provide their documented integration evidence; they do not authorize testnet/mainnet submission or certify a production deployment.

## Diagnostic contract for tools

Use `--json` for automation. A normal handled response is exactly one JSON object on stdout with a trailing newline and no stderr output. Its required envelope fields are `schema_version`, `command`, `ok`, `diagnostics` and `result`. On failure `result` is null; on success `diagnostics` is empty. Diagnostic fields are `code`, `severity`, `message`, `source`, `span` and `notes`. The current compiler reports one error at a time; clients should still consume the diagnostics array.

Match diagnostic codes and exit status, not exact English messages, JSON property order or whitespace. `source` is a basename or null, never a promise of a unique full filesystem path. `span` is null when no source location is available. Located spans are half-open offsets in original UTF-8 bytes; line and column are one-based Unicode-scalar positions. Tabs count as one column, CRLF as one newline, and an initial BOM consumes bytes without a displayed column. Notes are strings whose wording may evolve. Human diagnostics go to stderr as `source:line:column: CODE: message` when located, otherwise `CODE: message`; notes follow on indented lines. Current human success output is an unwrapped JSON result on stdout. Neither normal mode emits color escapes.

| Exit | Meaning | Representative code |
| --- | --- | --- |
| 0 | Success | No diagnostic |
| 1 | Source, type, fixed binding or solution conversion failure | E0200, E0301, E0300 |
| 2 | Command usage or unsupported compatibility identifier | E0400 |
| 3 | CLVM execution/validation or cost failure | E0500, E0501 |
| 4 | File access or artifact integrity/provenance failure | E0600 |
| 70 | Handled internal compiler invariant failure | E9000 |

Exit 70 describes a handled E9000 diagnostic; it does not promise that every OS termination, Rust panic, broken pipe or external resource failure becomes a structured response. Those remain failures to investigate. Raw malformed serialization can fail conversion with E0300, while valid serialized data rejected by generated CLVM guards can fail execution with E0500. Generated on-chain raises do not carry a source-level diagnostic contract.

## Regression evidence and native Linux commands

`crates/cli/tests/diagnostic_contract.rs` adds three executable CLI tests: Unicode/BOM/CRLF/tab locations and human/JSON stream parity; representative exit/code categories, absent locations and failed-build nonpublication; and version identifiers plus successful output streams. The existing artifact metadata matrix covers compatibility/provenance rejection. No deliberate internal panic or E9000 injection is added.

Windows: the three new tests, workspace format/lint checks and full Rust suite are required. Native Linux must run the same new tests through the full workspace suite. From the existing native checkout, refresh these test-only changes from the known Windows share:

```bash
set -e
test -f Cargo.toml
rsync -a /mnt/artoo/e/DEV/0xBASIC/crates/cli/tests/ crates/cli/tests/
export CARGO_TARGET_DIR="$HOME/.cache/0xbasic/target"
cargo fmt --all -- --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
```

Expected totals: 277 Windows / 278 Linux Rust tests (three added). The `diagnostic_contract` integration test executable reports three passed. No Python package install or simulator rerun is needed for this test/documentation-only checkpoint. The test command builds required executables; no separate build step is necessary.

Windows verification (2026-10-24): all 277 Rust tests passed, including all three new diagnostic-contract tests; `cargo fmt --all -- --check`, workspace Clippy with warnings denied, and `git diff --check` passed. The user subsequently confirmed native Linux verification passed (278 tests). M5-2 is complete.
