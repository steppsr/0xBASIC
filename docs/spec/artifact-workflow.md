# Inspecting, rebuilding and comparing artifacts

This walkthrough uses the payment example bundled with [the experimental release](experimental-release.md), compiler `0.1.0-m3.8b`. It demonstrates a rebuild with the same compiler. It does not claim compatibility with a future compiler or perform a coin migration.

## Preserve the original inputs

Keep the exact `.bas` source bytes, fixed bindings, any solution data, the complete artifact directory and the compiler/toolchain/dependency provenance. The manifest describes these inputs but does not contain the source or authenticate it. Retain the matching compiler and source bundle when you need to reproduce an older artifact.

For this exercise, extract a fresh native release package and work from its root. `original-build` and `rebuilt-build` must not already exist. The following commands use the Linux executable name; on Windows replace `./bin/0xbasic` with `./bin/0xbasic.exe`. Commands and JSON flags are otherwise identical. No Rust toolchain or node is needed. Python is only needed for the optional comparison script below.

## Inspect before building

```text
./bin/0xbasic --version
./bin/0xbasic check examples/height-locked-payment.bas --json
./bin/0xbasic explain examples/height-locked-payment.bas --stage clvm --bindings examples/height-locked-payment.bindings.json --json
```

`--version` reports compiler, language, ABI and target-profile identities. It does not accept `--json`. Checking needs no bindings; inspecting bound CLVM does. `explain` produces template/puzzle bytes and hashes in memory without creating artifacts or executing the puzzle. Its debug representation is compiler-versioned.

## Build twice into new directories

```text
./bin/0xbasic build examples/height-locked-payment.bas --bindings examples/height-locked-payment.bindings.json --out original-build --json
./bin/0xbasic run original-build/manifest.json --json
./bin/0xbasic build examples/height-locked-payment.bas --bindings examples/height-locked-payment.bindings.json --out rebuilt-build --json
./bin/0xbasic run rebuilt-build/manifest.json --json
```

Each build returns relative artifact filenames and template/puzzle descriptions. Each run should return `ok: true`, `validation: "clvm-execution-only"` and cost `1487727` for these exact inputs. The example has no solution fields, so the default empty solution is sufficient. See the [payment tutorial](payment-tutorial.md) for the condition tree and signing/confirmation distinction.

The build command refuses to overwrite an existing output directory. Preserve the original and choose a new candidate directory for subsequent attempts; do not edit its manifest to make it pass a different reader.

## Compare bytes, identities and provenance

Save the following as `compare-artifacts.py` in the package root and run `python3 compare-artifacts.py` on Linux or `python compare-artifacts.py` on Windows. It reads files and prints comparisons; it does not modify artifacts or decide whether an upgrade is safe.

```python
import json
from pathlib import Path

old = Path("original-build")
new = Path("rebuilt-build")
before = json.loads((old / "manifest.json").read_text(encoding="utf-8"))
after = json.loads((new / "manifest.json").read_text(encoding="utf-8"))
for name in ("template.clvm", "template.hex", "puzzle.clvm", "puzzle.hex", "manifest.json"):
    print(name, "identical:", (old / name).read_bytes() == (new / name).read_bytes())
for name in ("compiler", "source", "language_version", "abi_version", "target_profile",
             "optimization", "fixed_parameters", "inputs", "bindings"):
    print(name, "unchanged:", before[name] == after[name])
for role in ("template", "puzzle"):
    for kind in ("program_sha256", "tree_hash"):
        print(role, kind, "old:", before[role][kind], "new:", after[role][kind])
```

All `identical` and `unchanged` comparisons should be `True` for the same-version exercise above. The comparison script assumes two successful bound builds; it is not an artifact validator. The preceding `run` commands exercise each artifact reader's integrity checks.

For the released payment example, the bound puzzle values are:

| Field | Expected value |
| --- | --- |
| Serialized-byte SHA-256 (`program_sha256`) | `6949a6a511716438d9afaf30fb60ef57e1c7a1026cf47affc4c5d934055c0e81` |
| CLVM tree hash (`tree_hash`) | `f8bac319ef0beaf4dacbd7b0770d115d013a97a25f8656cb350280698a25ccea` |

These are different hashes with different purposes. A source line-ending change can alter provenance without changing the generated puzzle. A compiler/toolchain change can alter provenance and may also alter generated bytes. Compare the actual files and fields rather than treating a whole-manifest difference as proof that puzzle identity changed.

## When evaluating a future upgrade

Use the old compiler to inspect/run the old artifact and the candidate compiler to rebuild the preserved source into a new directory. The current reader requires exact compiler and other compatibility identities; do not expect the new executable to run old manifests automatically. Do not edit version fields to bypass this check.

| Observation | Interpretation and next action |
| --- | --- |
| Source rejected by the candidate compiler | Review its explicit migration rules; preserve the original before changing source |
| Provenance differs but program bytes/hashes match | Record the changed compiler/toolchain/source inputs; matching output does not waive compatibility review |
| Template or bound puzzle bytes/hash differ | Investigate the documented code-generation or binding change and rerun applicable conformance checks |
| Bound puzzle tree hash differs | This identifies a different puzzle; rebuilding does not update the rules of an existing coin |
| Local execution succeeds | Only local execution is established; signed spend/block validation remains a separate check |

Retain the original reveal and tooling for existing coins. Any move to a new puzzle requires a separately designed, authorized spend satisfying the existing puzzle; this guide supplies no wallet or migration transaction. See [experimental compatibility](experimental-compatibility.md) and [manifest validation](manifest-validation.md).
