# FOR/NEXT public-activation compatibility plan

Status: selected implementation plan, 2026-10-26. **This document does not enable loops.** The public compiler remains `0.1.0-m3.8b`, language `0.1`. The [private depth/golden checkpoint](for-next-hardening.md) passed Windows and native Linux, including exact program hash, cost and result parity, and was published as `f50f2eb`.

## Selected identities

| Language | `0.1` | `0.2` |
| ABI | `1` | `1`, subject to unchanged boundary/currying validation |
| VM profile | `chia-clvm-0.19-strict-v1` | Unchanged; pinned dialect, flags and dependency versions |
| Manifest and CLI envelope schema | `1` | `1`; no structural schema change is planned |
| Optimization identity | `none` | `none`; required loop lowering is not an optional optimizer |

The compiler and language identities change because accepting FOR/NEXT and reserving four existing identifiers changes the source contract. AST/IR inspection remains compiler-versioned rather than a stable interchange schema. Preserve the schema identifier only while its documented structure remains compatible; do not use this plan to conceal a later schema or ABI change.

`0.2.0-alpha.1` is the selected next compiler target, not a claim that it is already built, published or production-ready. No tag, GitHub release or replacement asset is authorized by this document. Preserve the existing experimental tag and assets. Once the new compiler is published, later behavior or generated-byte changes need a distinct compiler prerelease identity under the [existing compatibility policy](experimental-compatibility.md).

## Source migration

FOR, TO, STEP and NEXT become reserved everywhere identifiers are accepted, case-insensitively. Existing declarations and references using any of those names must be renamed before compiling with language 0.2. This includes contract/function names, fixed and solution fields, function parameters, DIM/CONST locals, assignments and name expressions. String values and comments do not require renaming.

For example, language 0.1 may use `DIM step = 1`; migrate the declaration and its references to `DIM stride = 1`. A loop-capable program can then use `FOR index = 1 TO 3 STEP stride` with a matching `NEXT index`. Do not apply blind text replacement to strings, comments or substrings of other identifiers.

Renaming a fixed/solution field also requires updating its JSON binding/solution keys. Preserve declaration order where the ABI depends on it, rebuild into a new output directory, and compare program bytes and tree hashes. A source rename is not a promise of unchanged puzzle identity. The existing compiler remains the tool for reading its original artifacts; do not edit version fields in a manifest to bypass compatibility checks.

No legacy-language switch or partial public loop feature flag is planned. The new default parser and the compiler identities must change in the same activation checkpoint.

## Artifact and inspection behavior

The artifact reader currently requires exact compiler and language identities. Keep that policy: the new reader rejects old-version manifests with E0400/exit 2, and the old reader rejects new-version manifests. This remains true when a non-loop program happens to compile to identical CLVM bytes. Preserve old artifacts and matching tools for existing puzzles; a new puzzle hash does not update an existing coin's rules.

The manifest structure remains unchanged: it records the new producer and language identities using its existing fields. ABI encoding, declaration-order fields, currying, raw input validation, hash checks and no-overwrite behavior must remain intact. Rebuild rather than relabel artifacts.

For `explain --stage ast`, promote the existing flat For node with counter/header/NEXT spans, start/end expressions, optional explicit step, and body references. AST inspection still parses without semantic analysis; a missing step remains distinguishable from an explicit `1`.

For `explain --stage ir`, expose checked loop headers, typed captures, body values, outputs and return-state linkage through the versioned IR representation. Header snapshots and counter/default-step bindings are lowering details; explain their meaning without promising stable numeric IDs. The analyzer's conservative assignment/effect metadata remains internal and must not accidentally become a new serialized public API.

For `explain --stage clvm`, require generated bytes/hashes to agree with build artifacts for the same normalized bindings. `run` keeps its current local-execution scope and error mapping: entered zero step is E0500, exhausted VM budget is E0501. The 256 syntactic EMIT limit must not become a runtime condition cap. Existing output serialization/display limits still apply.

## Activation implementation checklist

This is one coherent public-behavior checkpoint, prepared locally and validated before publication:

1. Separate reusable parser, analysis, IR and CLVM loop code from unit-test helpers. Promote implementation modules and variants without promoting fixture generators, the private source helper, subprocess workers or counter instrumentation. Retain VM counters as a dev-dependency only.
2. Remove the private parser switch and whole-module loop rejection. Make all normal public parse/analyze/check/compile paths use the complete implementation, including functions, nested returns, emission assembly and existing compiler budgets. Replace tests that require public rejection with positive public API tests; retain malformed, unreachable and compatibility negatives.
3. Update workspace/package identities and lockfile package entries, compiler language/subset constants, manifest language schema, CLI version/diagnostic fixtures, tutorial verifier expectations and package identity assertions together. Package filenames are derived from the workspace version; verify that derivation rather than introducing a second hard-coded identity.
4. Update grammar and normative language documentation for language 0.2, while preserving the 0.1 document as historical documentation for the existing release. Add exact public loop examples, keyword migration and new failure/resource rules to CLI, inspection, compatibility and tutorial documentation. Clearly label which release each tutorial targets.
5. Exercise loops through ordinary library and CLI integration tests, not just unit-test-only entry points. Include check/build/run, every explain stage, template-only and fixed/solution binding, default/negative/zero step, nested conditions/returns, unused input validation, no-overwrite behavior and handled JSON diagnostics. Add old/new manifest identity rejection cases.
6. Keep the four loop goldens and existing non-loop production regressions. Verify public compilation matches the private loop baseline or document each justified byte/cost change before updating expectations. Separate producer/provenance changes from actual program/hash changes.
7. Run formatting, Clippy, workspace and CLI regressions on Windows, then give the user exact native Linux synchronization/test commands. The activation handoff must include every changed manifest, lockfile, source, fixture and verifier input; the earlier source-only copy is not sufficient for a version change.
8. Publish only after the native gate passes, then verify exact-revision GitHub CI. Update the resume checkpoint and current-status documents with the actual revision and results.

Readiness is based on completing this checklist, not simply removing `cfg(test)` from files that currently mix implementation and test helpers.

## Integration and release gates after activation

- Add a representative authorized loop-generated payment/condition scenario to the isolated spend/full-node harness, including valid and adversarial inputs and exact coin/condition expectations. Local VM tests alone do not establish spend acceptance.
- Run source-inclusive package creation, offline original/modified-library rebuilds and extracted CLI/tutorial checks on both platforms at the intended candidate revision. Include all loop source and fixtures in inventory checks.
- Update migration, release notes, tested-platform scope and source/license notices as needed. Preserve the older release and its tooling.
- Prepare a concrete candidate and obtain the separate release-publication approval required by the release workflow. No network transaction or production deployment is part of compiler activation.
